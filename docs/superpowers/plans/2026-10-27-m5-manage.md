# M5 Manage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in user creates folders, renames, moves, copies and deletes files and folders, one at a time from a row menu (right click or ⋯) or several at once from a selection bar. Long moves and copies run as server-side tasks whose progress shows in the same floating panel as uploads, and name conflicts are settled with Replace, Keep both or Cancel, with "apply to all".

**Architecture:** New folder and rename are synchronous JSON endpoints in `browse`. Delete, copy and move are background tasks of a new `tasks` server domain: an in-memory, per-user registry that runs at most two tasks at once on Tokio's blocking pool, reports progress through atomics and is polled by the web app. All filesystem work stays in `storage` (`delete.rs`, `transfer.rs`). A copied file is staged in the destination volume's `.explorer-uploads` and committed with the same no-replace rename as an upload. The web app gets a selection model, a row actions menu, dialogs built on the native `<dialog>` element, a folder picker, a task store polled while tasks run, and an activity panel that holds uploads and tasks.

**Tech Stack:** Existing M4 stack. Server: no new crate unless a task says so (`axum-extra` with the `query` feature is allowed for repeated query parameters in Task 4). Web: more `web-sys` features (`HtmlDialogElement`, `KeyboardEvent` if needed).

**Spec:** `docs/superpowers/specs/2026-10-18-explorer-design.md` (milestone 5 of §14; §7 selection bar, context menu, mobile ⋯ and "+", confirmations; §9 name conflicts, move/copy tasks, cross-volume moves, delete; §11).

## Global Constraints

- Everything from the M1–M4 plans' Global Constraints still applies: English, sparse comments, no commit rewriting, owner merges, no personal data, `cargo xtask ci` passes before the PR, no UI control that does not work end to end, all filesystem access through `storage`, blocking cap-std calls in `spawn_blocking`, no `document::eval`, unit tests inline.
- **One branch, one PR:** branch `m5/manage`, based on `refactor/domain-layout` (PR #65, not merged yet). **One commit per task**, subject as given in the task; a fix after review is its own follow-up commit.
- **Domain layout** (owner rule): code goes into its domain folder. Server: `browse/` (folders, rename), `tasks/` (new), `storage/` (`delete.rs`, `transfer.rs` new). Shared DTOs: `shared::api::conflict` (new), `shared::api::browse`, `shared::api::tasks` (new). Web: `src/selection.rs`, `src/conflict.rs`, `src/tasks/` (new), `components/manage/` (new), `components/tasks/` (new). Split a file that passes ~400 lines of non-test code.
- No UI element from M6: no search, grid toggle, favorites, thumbnails, preview item in menus.
- **Conflict policies** for rename, copy and move are the upload ones: `fail` (default), `replace`, `keep_both`, same `Name (n).ext` rule up to `(999)`. **Replace only replaces a file by a file**: when the source or the existing target is a folder, the server answers 400 `is_a_directory` and the conflict prompt does not offer Replace. A target that appears after the conflict check is never overwritten under `fail` or `keep_both`: the final rename uses no-replace semantics and falls back to keep-both naming, as uploads do.
- **Write access:** rename, move (source and destination), delete and new folder need `Action::Write` on their volume (403 `read_only_volume` on a read-only one); copy needs `Read` on the source and `Write` on the destination. Read-only volumes hide write actions in the UI.
- **Reserved paths:** no operation may take the volume root or anything under `.explorer-uploads` as a source, and no rename or destination may produce one (`invalid_path` / `path_not_found`, as today).
- **Symlinks:** delete, rename and same-volume move act on the link itself, never on its target. Copy (and the copy half of a cross-volume move) follows the `walk` rules: symlinks to files inside the volume are copied as files; symlinks to directories, sockets, FIFOs and devices are skipped and counted in `skipped`.
- **Move into itself:** moving or copying a folder into itself or one of its descendants is 400 `invalid_destination`, checked on paths at creation and by mapping the kernel's `EINVAL` on rename.
- **New JSON error codes:** `invalid_destination` 400, `task_not_found` 404. Each gets an `error-<code>` translation in en/fr/es.
- **Logging:** each operation logs at `info` with `user`, `action` (`create_folder`, `rename`, `delete`, `copy`, `move`), `volume`, `path`, and where relevant `dest_volume`, `final_path`, `files`, `bytes`, `skipped`; failures at `warn`. Never log file contents.
- **Dialogs** use one shared `Modal` component on the native `<dialog>` element opened with `HtmlDialogElement::show_modal()` (focus trap, inert background, Escape, focus restored on close: the M4 conflict dialog follow-up). **Menus** use one shared `Menu` component with `role="menu"`, arrow-key navigation (Up/Down/Home/End), Escape and focus restore (the M4 upload-menu follow-up).
- Every new UI string exists in `en-US.ftl`, `fr-FR.ftl` and `es-ES.ftl`; the existing "every key in every locale" test keeps passing.

## Review Focus

1. **Deleting a symlink.** Deleting a symlink to a folder inside the volume, to a file, or to something outside the volume removes the link only; the target and its contents are untouched. Tests in Task 5 (`delete_removes_symlink_not_target`).
2. **Moving or copying a folder into itself.** `A` into `A` or `A/sub`, including through a symlink to `A`, gives `invalid_destination` and changes nothing. Tests in Tasks 6 and 7 (`copy_into_itself_is_refused`, `move_into_descendant_is_refused`).
3. **Cross-volume move with entries copy cannot take.** A folder holding a symlink to a directory or a FIFO is moved to another volume: everything copyable arrives, the skipped entries and the folders that still hold them stay in the source, nothing is lost. Test in Task 7 (`cross_volume_move_keeps_what_it_skipped`).
4. **A target that appears while a task waits or runs.** Under `fail` or `keep_both` the existing file is never replaced; the result gets a `(n)` name and `final_path` says so. Tests in Tasks 6 and 7.
5. **Cancelling a copy of a large file.** The staged file is removed, the partial destination tree of a copy is removed, nothing half-written ever appears under the final name. Test in Task 6 (`cancelled_copy_leaves_nothing`).

  ```rust
  pub struct Location { pub volume: String, pub path: String }
  #[serde(tag = "op", rename_all = "snake_case")]
  pub enum TaskSpec {
      Delete { source: Location },
      Copy { source: Location, dest_dir: Location, #[serde(default)] conflict: ConflictPolicy },
      Move { source: Location, dest_dir: Location, #[serde(default)] conflict: ConflictPolicy },
  }
  #[serde(rename_all = "snake_case")] pub enum TaskState { Queued, Running, Done, Failed, Cancelled }
  pub struct TaskInfo {
      pub id: String, pub spec: TaskSpec, pub state: TaskState,
      pub files_done: u64, pub files_total: Option<u64>,
      pub bytes_done: u64, pub bytes_total: Option<u64>,
      pub skipped: u64,
      pub final_path: Option<String>, // copy/move: where the entry ended up
      pub error: Option<ErrorBody>,   // set when Failed
  }
  // storage::Volume (delete.rs)
  /// Removes a file, a symlink (never its target) or a whole folder tree.
  pub fn delete(&self, path: &RelPath) -> Result<(), StorageError>;
  // server tasks
  pub const MAX_RUNNING: usize = 2;
  pub const FINISHED_TTL: Duration = Duration::from_secs(3600);
  pub struct Tasks { /* Mutex<HashMap<TaskId, Entry>>, Semaphore */ }
  impl Tasks {
      pub fn new() -> Self;
      pub fn list(&self, user: &str) -> Vec<TaskInfo>;            // creation order, prunes finished older than FINISHED_TTL
      pub fn cancel_or_dismiss(&self, user: &str, id: &str) -> bool; // false: unknown or another user's
  }
  pub struct Progress { /* atomics: files_done, bytes_done, skipped; cancelled: AtomicBool */ }
  impl Progress { pub fn is_cancelled(&self) -> bool; pub fn add_file(&self, bytes: u64); pub fn add_bytes(&self, n: u64); pub fn skip(&self); }
  // AppState gains `pub tasks: Arc<Tasks>`
  // web crate::tasks
  pub struct TaskStore; // context, like Uploads: start(spec_batch), decide, cancel, dismiss, poll loop
  ```

  - `GET /api/tasks` → the caller's tasks. `DELETE /api/tasks/{id}` → 204: cancels a queued or running task (state `cancelled` once its runner notices), removes a finished one; 404 `task_not_found` for unknown ids or another user's (ids are 128 random bits, hex).
  - A task waits for a `Semaphore` permit (`MAX_RUNNING`), then runs its op in `spawn_blocking` with the request span's fields; state goes `queued → running → done | failed | cancelled`. Task 5 implements `Delete`; until Tasks 6 and 7 replace that match arm, `Copy` and `Move` answer 404 `not_found` and no UI offers them.
  - `delete`: refuses root and reserved paths; opens the parent directory (confined, following), looks at the last component with `symlink_metadata` (not following): a real directory goes through cap-std `remove_dir_all` on the parent handle, anything else through `remove_file`. Delete sets `files_total` to `Some(1)` and `files_done` to 1 on success.
  - Tasks are in memory; a restart loses them (logged at startup as nothing to recover; staged copy files left behind are swept after 24 h by the existing orphan sweep).
  - Web: `TaskStore` polls `GET /api/tasks` every 1 s while a task of this tab is queued or running, stops otherwise, and bumps `Revision` when one finishes. Delete asks for confirmation in a `Modal` naming the entry, or "N items", with a red Delete button; on confirm it posts one task per selected entry and clears the selection.

Closing clears finished uploads and dismisses finished tasks.

  ```rust
  pub struct TransferPlan { pub items: Vec<WalkItem>, pub files: u64, pub bytes: u64 } // a single file is one item
  pub fn plan_transfer(source: &Volume, path: &RelPath) -> Result<TransferPlan, StorageError>;
  /// Copies `path` of `source` into the folder `dest_dir` of `dest`, which may be the same volume.
  /// Returns the path the copy ended up at.
  pub fn copy(source: &Volume, path: &RelPath, dest: &Volume, dest_dir: &RelPath, conflict: ConflictPolicy, plan: &TransferPlan, progress: &dyn TransferProgress) -> Result<RelPath, StorageError>;
  pub trait TransferProgress { fn is_cancelled(&self) -> bool; fn add_bytes(&self, n: u64); fn add_file(&self); fn skip(&self); }
  /// Conflict check at task creation: Fail + existing target -> AlreadyExists; Replace with a folder on either side -> IsADirectory;
  /// dest_dir inside path (same volume) -> InvalidDestination; dest_dir must be an existing folder.
  pub fn check_transfer(source: &Volume, path: &RelPath, dest: &Volume, dest_dir: &RelPath, conflict: ConflictPolicy) -> Result<(), StorageError>;
  pub const COPY_CHUNK: usize = 1024 * 1024;
  ```
  - A file is streamed in `COPY_CHUNK` pieces into a file staged in the destination volume (`dest.staging()?.create(&StagedId::random())`), checking `is_cancelled` between pieces, then committed with `commit_staged(…, conflict, source modified time)`. A folder: the top folder is created with no-replace semantics (keep-both naming under `keep_both`, or under `fail` when it appeared after the check), then `plan.items` are replayed under it: folders with `create_dir`, files staged and committed with `Fail` (a fresh tree has no conflicts). Entries `walk` skips call `progress.skip()` (count them while planning: extend `walk` or count in `plan_transfer`, without changing what zip sees).
  - Cancel or failure: the staged file is removed; a copied folder's partial tree is deleted; a single copied file never reaches its final name.

The runner plans, sets `files_total`/`bytes_total`, copies, sets `final_path`; logs `copy` with `files`, `bytes`, `skipped`, `final_path`.
  - Folder picker (`Modal`): starts in the current folder; lists writable volumes and the folders of the shown folder (the entries API, folders only), breadcrumb, a confirm button "Copy here" / "Move here". For a copy every folder is allowed (copying into the same folder then asks the conflict question, and Keep both makes a duplicate) except the source folders themselves and their descendants, which are shown disabled.
  - Web conflicts: a 409 on `POST` marks the item `NeedsDecision`; `ConflictPrompt` asks (Replace only when source and existing target are files, from the selection's kinds and the conflict details), with "apply to all" across the items of the same user action; the item is resent with the policy or dropped on Cancel.
