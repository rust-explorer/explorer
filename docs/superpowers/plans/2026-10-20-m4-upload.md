# M4 Upload Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in user uploads files and whole folder trees (picker or drag & drop) into the current folder of a writable volume. Uploads of up to ~10 GB survive network drops and page reloads, show their progress and speed in a floating panel while the user keeps browsing, and name conflicts are settled with Replace, Keep both or Cancel, with "apply to all".

**Architecture:** The server implements the tus 1.0 core protocol with the creation and termination extensions under `/files/uploads`. Upload state lives in SQLite (`uploads` table) and the bytes in a hidden staging directory `/data/<volume>/.explorer-uploads/<id>`. A finished upload is committed with an atomic rename into place, creating missing folders. All filesystem work stays in `storage`. The web app gets a host-testable upload engine (a reducer that turns events into effects), a wasm-only transport (XHR for upload progress, fetch for the rest), the floating uploads panel, the Upload button, the conflict dialog and drag & drop.

**Tech Stack:** Existing M3 stack, plus base64 0.22 in `shared`, `rand` 0.8 as a normal server dependency; web: wasm-bindgen, wasm-bindgen-futures, gloo-timers 0.3 (`futures`), more web-sys features (File, Blob, XMLHttpRequest, DataTransfer, FileSystem*Entry…).

**Spec:** `docs/superpowers/specs/2026-10-18-explorer-design.md` (milestone 4 of §14; §5.3 tus, §7 Upload button, drag & drop, floating uploads panel, mobile "+" button; §8; §9 uploads, folder uploads, name conflicts; §11).

## Global Constraints

- Everything from the M1–M3 plans' Global Constraints still applies: English, sparse comments, no commit rewriting, one stacked branch + PR per task (`m4/<slug>`, the first one based on `m3/docs` because M3 is not merged yet), owner merges, no personal data, `cargo xtask ci` passes before each PR, no UI control that does not work end to end, all filesystem access through `storage`, blocking cap-std calls in `spawn_blocking`.
- No UI element from a later milestone: no New folder button (the folders endpoint exists for folder uploads only), no checkboxes, selection bar, context menu, search, grid toggle or favorites. The mobile "+" button offers only the upload choices.
- tus: `Tus-Resumable: 1.0.0` is required on every request to `/files/uploads*` except `OPTIONS`, and sent on every response from it. Extensions: `creation`, `termination`. No `Upload-Defer-Length`, no `creation-with-upload`, no checksum.
- `Upload-Metadata` keys (values base64, standard alphabet with padding): `volume` and `path` required, `modified` (client `lastModified`, integer milliseconds) and `conflict` (`fail` default, `replace`, `keep_both`) optional; unknown keys are ignored. `path` is the destination file path relative to the volume, including the file name.
- Chunk size: 16 MiB (`16 * 1024 * 1024`). At most 3 files upload at once. Retry delay after a transient failure: `min(1 s × 2^(attempt-1), 30 s)`, retried until the user cancels.
- Staging directory name: `.explorer-uploads`, mode 0o700, at each volume root, created on first upload. It never appears in listings or zips, and `RelPath::parse` rejects any path whose first component is that name (`invalid_path`, reason `reserved name`). Abandoned uploads are deleted 24 h after their last activity; the sweep runs at startup and every hour.
- "Keep both" names: `Film.mkv` → `Film (1).mkv`, then `(2)`…; the suffix goes before the last extension; a name whose only dot is the first character has no extension (`.bashrc` → `.bashrc (1)`). Up to `(999)`, then `already_exists`.
- Replace never replaces a folder. Folders already present are merged into, never a conflict.
- The final file gets the client's `modified` time when given.
- New JSON error codes: `already_exists` 409, `read_only_volume` 403, `insufficient_storage` 507, `upload_not_found` 404, `offset_mismatch` 409, `upload_busy` 423, `upload_too_large` 413, `invalid_upload` 400, `unsupported_tus_version` 412, `unsupported_media_type` 415. Each has an `error-<code>` translation in en/fr/es.
- Logging: upload started / completed / cancelled, folder created, and each sweep that removed something at `info` with `user`, `action`, `volume`, `path` (and `bytes`, `final_path` on completion); failures at `warn`. Never log file contents or metadata values other than those fields.
- Dynamic sizes in the DOM (progress bars) go through Dioxus style properties only; no `document::eval`, no inline script; uploads use same-origin XHR/fetch only (the CSP's `connect-src 'self'`).

## Review Focus

1. **A network drop in the middle of a 16 MiB chunk.** The server keeps the bytes it received, releases the upload's lock, and `HEAD` reports the new offset; the client resumes from there instead of failing or restarting at zero. Tests in Task 4 (`resume_after_interrupted_patch`) and Task 5 (`transient_patch_failure_resyncs_with_head`).
2. **Hostile destination paths.** `../x`, `/etc/x`, `a/../../x`, `.explorer-uploads/x`, a NUL byte, or a parent that is a symlink escaping the volume, in upload metadata or the folders endpoint, give `invalid_path` / `outside_volume` and write nothing outside the volume. Tests in Task 2 and Task 4.
3. **Conflicts.** A file that appears between creation and commit is never overwritten without Replace; Replace never replaces a folder; Keep both handles dotfiles and multi-dot names. Tests in Task 2.
4. **Reload, then re-select the same file or folder.** The upload resumes when volume, path (including the folder-relative part), size and modified time all match; a different modified time starts a new upload. Tests in Task 5 (`resumes_matching_pending_upload`, `changed_file_is_not_resumed`).
5. **Folder trees with empty folders, 0-byte files and thousands of entries.** Empty folders are created, 0-byte files complete without a PATCH, at most 3 transfers run at once, and the listing refresh is throttled. Tests in Task 4 (`zero_length_upload_completes_on_creation`) and Task 5 (`plan_batch_*`, `runs_at_most_three_transfers`, `refresh_is_throttled`).

  ```rust
      pub fn remove(&self, id: &UploadId) -> Result<(), StorageError>;                     // missing is Ok
      pub fn files(&self) -> Result<Vec<(String, SystemTime)>, StorageError>;               // name and mtime of every entry
  }
  // storage::write (blocking, like ops)
  impl Volume {
      pub fn create_dir_all(&self, dir: &RelPath) -> Result<(), StorageError>;
      pub fn check_upload_target(&self, path: &RelPath, conflict: ConflictPolicy) -> Result<(), StorageError>;
      pub fn staging(&self) -> Result<Staging, StorageError>;                // creates the dir if needed
      pub fn existing_staging(&self) -> Result<Option<Staging>, StorageError>; // never creates
      pub fn commit_upload(&self, staging: &Staging, id: &UploadId, dest: &RelPath, conflict: ConflictPolicy, modified: Option<SystemTime>) -> Result<RelPath, StorageError>; // the final path
  }
  pub fn keep_both_name(name: &str, n: u32) -> String;
  ```
  How each operation behaves:
  - **`create_dir_all`.** Creates each missing component in turn. A component that exists as a folder (or a symlink resolving to one inside the volume) is fine. The full path existing as a file → `AlreadyExists(path)`. An ancestor that is a file → `NotADirectory(ancestor)`. Escapes → `OutsideVolume`.
  - **`check_upload_target`.** The parent chain may be missing (it will be created). An ancestor that is a file → `NotADirectory`. Then by policy: `Fail` and anything exists at `path` → `AlreadyExists`; `Replace` and `path` is a folder → `IsADirectory`; otherwise `Ok`.
  - **`staging`.** The directory is opened without following symlinks (`open_dir_nofollow`); a symlink or a non-directory named `.explorer-uploads` is an error, never followed.
  - **`commit_upload`.**
    1. `create_dir_all(dest.parent())`, then open the parent as a `Dir`.
    2. Set the staged file's mtime to `modified` when given, then `sync_all`.
    3. `Replace`: if `dest` is a folder → `IsADirectory`; otherwise `renameat` from the staging `Dir` to the parent `Dir` (atomic replace).
    4. `Fail` and `KeepBoth`: rename without replacing (`renameat_with`, `RenameFlags::NOREPLACE` on Linux, `EXCL` on macOS), trying the name, then `keep_both_name(name, 1..=999)`; `EEXIST` moves to the next name. Under `Fail` this only happens when a file appeared after creation (logged at `info`), which is a deliberate "keep both" rather than an overwrite or a lost upload.
    5. Both sides of the rename are `Dir` handles plus a single file name, so nothing is resolved through symlinks there; an `EXDEV` (the parent is another mount nested in the volume) is an `Io` error whose log says the destination is on another filesystem than the volume.
  - **Listing and walk.** `entries()` of the root drops `STAGING_DIR`, so it is hidden from `list`, `walk` and zips.

  ```rust
  // shared::tus
  pub const TUS_VERSION: &str = "1.0.0";
  pub fn encode_metadata(pairs: &[(&str, &str)]) -> String;                       // "volume bWVkaWE=,path YS50eHQ="

  ```
  Routes:
  - `OPTIONS /files/uploads` → 204, `Tus-Version: 1.0.0`, `Tus-Extension: creation,termination`.
  - `POST /files/uploads` (creation):
    - `Upload-Length` (decimal) is required → else 400 `invalid_upload`;
    - metadata as in Global Constraints;
    - `authorize(Write)`; an empty `path` is `invalid_path`;
    - `length` greater than the volume's available space → 507 `insufficient_storage`;
    - `check_upload_target` → `already_exists` / `is_a_directory` / `not_a_directory` with `details {volume, path}`;
    - creates the staged file and the record; a 0-byte upload is committed at once;
    - answers 201 with `Location: /files/uploads/<id>` and `Upload-Offset: 0`.
  - `HEAD /files/uploads/{id}` → 200, `Upload-Offset` (the staged file's length, or the length once committed), `Upload-Length`, `Cache-Control: no-store`. An unknown id, another user's, or a pending one whose staged file is gone → 404 `upload_not_found` (the orphan record is deleted).
  - `PATCH /files/uploads/{id}`:
    - `Content-Type: application/offset+octet-stream` → else 415; `Upload-Offset` required → else 400 `invalid_upload`;
    - unknown → 404; `authorize(Write)` on the record's volume and path;
    - already committed: offset equal to the length → 204 with that offset, otherwise 409 `offset_mismatch`;
    - `try_lock` → else 423 `upload_busy`; offset different from the staged length → 409 `offset_mismatch` with `details.offset`;
    - streams the body into the staged file frame by frame; no frame for `PATCH_IDLE_TIMEOUT` (60 s) ends the request like a disconnect; a body error or disconnect keeps what was written;
    - bytes past `Upload-Length` → 413 `upload_too_large`, with the bytes up to the length kept;
    - after the body: `sync_data`, `touch`; when the offset reaches the length, `commit_upload` then `mark_done`;
    - a commit failure answers its mapped error and leaves the staged file complete, so a later empty PATCH at `offset == length` retries the commit;
    - answers 204 with `Upload-Offset`.
  - `DELETE /files/uploads/{id}` → 204. A pending upload loses its staged file and record; a committed one only its record. Unknown → 404.
  - `GET /api/uploads` → `Vec<PendingUpload>` of the current user's pending uploads; records whose staged file is gone are left out.
  - `POST /api/volumes/{volume}/folders` with JSON `CreateFolder` → `authorize(Write)`, root is `invalid_path`, `create_dir_all`, 204. A malformed body is 400 `invalid_path`.
  - Every `/files/uploads*` response, errors included, carries `Tus-Resumable: 1.0.0`; a request other than `OPTIONS` without it, or with another version, gets 412 `unsupported_tus_version` with `Tus-Version`.

- Produces (all host-testable, no web-sys):
  ```rust
  pub const CHUNK_SIZE: u64 = 16 * 1024 * 1024;
  pub const MAX_PARALLEL: usize = 3;
  pub const REFRESH_EVERY_MS: i64 = 2000;
  pub fn retry_delay_ms(attempt: u32) -> i64; // 1000, 2000, 4000 … capped at 30_000
  // plan.rs
  #[derive(Debug, Clone, PartialEq)] pub struct PickedFile { pub relative: String, pub size: u64, pub modified_ms: Option<i64> } // relative = "" + name, or "Folder/sub/name"
  #[derive(Debug, Clone, PartialEq)] pub struct BatchPlan { pub files: Vec<FileSpec>, pub folders: Vec<String>, pub skipped: usize }
  #[derive(Debug, Clone, PartialEq)] pub struct FileSpec { pub volume: String, pub path: String, pub size: u64, pub modified_ms: Option<i64> }
  pub fn plan_batch(volume: &str, base: &str, files: Vec<PickedFile>, empty_dirs: Vec<String>) -> BatchPlan;
  // queue.rs
  #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)] pub struct ItemKey(pub u64);
  #[derive(Debug, Clone, Copy, PartialEq, Eq)] pub enum Decision { Replace, KeepBoth, Cancel }
  #[derive(Debug, Clone, PartialEq)] pub enum Status {
      Queued, NeedsDecision, Uploading, Retrying { attempt: u32, at_ms: i64 },
      Done, Failed(ApiFailure), Cancelled, Skipped,
  }
  #[derive(Debug, Clone, PartialEq)] pub enum Kind { File(FileSpec), Folder { volume: String, path: String } }
  #[derive(Debug, Clone, PartialEq)] pub struct Item { pub key: ItemKey, pub batch: u64, pub kind: Kind, pub status: Status, pub sent: u64, pub upload_url: Option<String>, pub conflict: ConflictPolicy }
  #[derive(Debug, Clone, PartialEq)] pub enum Effect {
      CreateFolder { key: ItemKey, volume: String, path: String },
      Create { key: ItemKey, spec: FileSpec, conflict: ConflictPolicy },
      Head { key: ItemKey, url: String },
      Patch { key: ItemKey, url: String, offset: u64, len: u64 },
      Abort { key: ItemKey },               // stop an in-flight request
      Delete { url: String },               // terminate on the server
      WakeAt { at_ms: i64 },                // call `tick` then
      Refresh { volume: String },
  }
  #[derive(Debug, Clone, PartialEq)] pub enum Event {
      FolderCreated { key: ItemKey },
      Created { key: ItemKey, url: String },
      Progress { key: ItemKey, sent: u64 },       // absolute bytes on the server side of this item
      Patched { key: ItemKey, offset: u64 },
      HeadDone { key: ItemKey, offset: u64 },
      Failed { key: ItemKey, failure: ApiFailure }, // classified below
      Decide { key: ItemKey, decision: Decision, apply_to_all: bool },
      Cancel { key: ItemKey },
  }
  #[derive(Debug, Default)] pub struct Queue { /* items, batch decisions, last refresh */ }
  impl Queue {
      pub fn add(&mut self, plan: BatchPlan, pending: &[PendingUpload], now_ms: i64) -> Vec<Effect>;
      pub fn handle(&mut self, event: Event, now_ms: i64) -> Vec<Effect>;
      pub fn tick(&mut self, now_ms: i64) -> Vec<Effect>;           // starts due retries

      pub fn pending_decision(&self) -> Option<&Item>;              // first NeedsDecision item

      pub fn is_active(&self) -> bool;                              // anything not finished
      pub fn clear_finished(&mut self);
  }
  // speed.rs
  pub struct SpeedMeter { /* samples (ms, bytes) over the last 5 s */ }
  impl SpeedMeter { pub fn record(&mut self, now_ms: i64, total_bytes: u64); pub fn bytes_per_sec(&self) -> Option<u64>; }
  ```
  Behaviour:
  - **`plan_batch`.**
    - Each file's path is `base` joined with its `relative`.
    - A relative path with an empty, `.` or `..` component is skipped and counted in `skipped`.
    - `folders` keeps only the empty dirs that are not an ancestor of a planned file, deduplicated, joined with `base`.
  - **Starting.** `add` creates one batch. Folder items are created first. A file whose `(volume, path, size, modified_ms)` equals a pending upload gets `upload_url = /files/uploads/<id>` and starts with `Head`; any other file starts with `Create` using the batch's apply-to-all decision if one is set, else `Fail`. At most `MAX_PARALLEL` items are `Uploading` at once; the others stay `Queued`.
  - **Transfer.** `Created` and `HeadDone` lead to a `Patch` of `min(CHUNK_SIZE, size - offset)` bytes; `Patched` leads to the next chunk, or to `Done` when `offset == size`. A 0-byte file is `Done` right after `Created`.
  - **Failures.** `Failed` is classified by the failure:
    - `Network`, `Http(5xx)` other than 507, `upload_busy`, `offset_mismatch` → `Retrying` with `retry_delay_ms` and a `WakeAt`; on wake an item with an `upload_url` sends `Head`, one without sends `Create` again;
    - `already_exists` on `Create` → the batch's decision if set (`Cancel` → `Skipped`), otherwise `NeedsDecision`;
    - `upload_not_found` on `Head` or `Patch` → the url is dropped and the item restarts with `Create` (once; a second time is `Failed`);
    - `unauthenticated` → `Failed` (the browser is already leaving for the sign-in page);
    - anything else (including 507 `insufficient_storage`, `read_only_volume`, `permission_denied`) → `Failed`.
  - **Decisions.** `Decide` sets the item's `conflict` (`Replace` → `replace`, `KeepBoth` → `keep_both`) and sends `Create`, or marks it `Skipped` for `Cancel`. With `apply_to_all`, the decision is stored for the batch and applied to every other `NeedsDecision` item in it.
  - **Cancel.** A queued, waiting or retrying item becomes `Cancelled`. An uploading one also gets `Abort`, and `Delete` when it has an `upload_url`. A finished item is unchanged.
  - **Refresh.** When an item of volume V reaches `Done`, `Refresh { volume: V }` is emitted if the last refresh was at least `REFRESH_EVERY_MS` ago, or if no item of V is still active.
